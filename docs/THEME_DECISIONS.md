## 一、待拍板（按影响面排序）

### Q1 · 本期做到哪一级？【最关键】

| 选项 | 内容 | 工作量 |
|---|---|---|
| **A（推荐）** | L0 调色 + L1 布局参数 | 小 |
| B | + L2 声明式布局重排（SDUI） | 中 |
| C | + L3 脚本层（theme.js） | 大 |

**建议：A。** 理由：
1. 你的 UI 页面已有 3,700+ 行（settings 913、discover 722、now_playing 594、plugin 490），**先把 Token 接进去本身就是不小的工作量**，且价值立即可见。
2. L2/L3 依赖 L1 稳定后的区域契约。现在定契约，很容易定错。
3. 生态需要先有"能用的皮肤"才有人来写花活。

**但架构必须为 B/C 预留位置**——这正是 `schemaVersion` 和"Layout 与 Token 正交"的意义。

---

### Q2 · 桌面歌词窗口是否纳入皮肤系统？

**背景**：`desktop_lyric_window.dart` 是 `desktop_multi_window` 的独立引擎 + 独立 `ThemeData`（写死 `Brightness.dark`），且已有 `DesktopLyricTheme`（4 个颜色 + `fromAccent` 取色逻辑）。

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **v1 不动歌词窗口**，仅从皮肤 token 派生其 accent。原 `DesktopLyricTheme` 保留 |
| B | v1 就打通，歌词窗口可独立指定皮肤 |

**建议：A。** 桌面歌词是 Windows-only 的独立窗口，跨引擎传递皮肤包（尤其背景图字节）成本高、收益低。但要做一件事：**让 `fromAccent` 的 accent 来自当前皮肤的 `color.brand.base`**——一行改动，就能让歌词窗口"跟着皮肤走"，零额外成本。

---

### Q3 · 官方内置皮肤做几个？

| 选项 | 内容 |
|---|---|
| A | 2 个（light / dark） |
| **B（推荐）** | 3 个：light / dark / **dynamic** |
| C | 5 个（+ 一个炫技的玻璃拟态 + 一个像素风） |

**建议：B。** `dynamic` 用 Material You 思路（从封面主色生成），它同时是**最好的能力展示**——证明 token 层能撑起动态配色。第 4、5 个留给 PR4 或社区贡献，不必占首发预算。

---

### Q4 · 是否做可视化调色器（GUI 编辑器）？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **本期不做**。先把格式和加载管线做扎实 |
| B | 本期做一个简易版（token 滑块 + 实时预览） |
| C | 做一个完整编辑器（含导出 .rtheme） |

**建议：A，但 JSON 结构必须为它设计。** 具体：token 用扁平的语义命名、值域明确（颜色用 hex / 数字用 number / 枚举用 string），这样将来写编辑器时是"遍历 schema 生成控件"，而不是硬编码每个字段。这是 Q1 选 JSON 而非代码的直接回报——**先把可能性留着，不急着兑现**。

---

### Q5 · 皮肤里的"用户可调旋钮"要不要做？

灵感来自 MusicFree 插件的 `userVariables`。皮肤可在 JSON 里声明：

```jsonc
"settings": [
  { "key": "blurAmount", "type": "range", "label": "模糊程度", "min": 0, "max": 40, "default": 12 },
  { "key": "accent",     "type": "color",  "label": "强调色",  "default": "#F2B749" }
]
```

App 自动在设置页生成滑块/取色器，用户拖一拖就能微调，**不用改 JSON、不用写 JS**。

| 选项 | 说明 |
|---|---|
| A | 本期不做 |
| **B（推荐）** | 本期做（成本低、收益高） |

**建议：B。** 这招非常划算——它是"用户自行设计"体验的**低成本入口**，比 GUI 编辑器便宜一个量级，却能让非技术用户立刻参与定制。而且它天然是纯数据，零安全风险。

---

### Q6 · 字体与自定义资源怎么管？

皮肤可能需要：自定义字体文件、背景图、装饰图。

| 选项 | 说明 |
|---|---|
| A | 只支持颜色，不支持资源 |
| **B（推荐）** | 支持 `background.image` + 可选 `font`，其余不支持 |
| C | 支持任意资源引用 |

**建议：B，且加限制**：单图 ≤ 500KB、整包 ≤ 10MB（沿用 MusicFree 的合理约束，它这块设得不错）。**字体只支持 1 个 family**，避免字体子集化和多字重带来的体积与兼容问题。

---

### Q7 · 皮肤如何持久化与切换？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | `UserSettings.activeThemeId` + 皮肤文件落在 `appSupport/themes/<id>/` |
| B | 皮肤也进 Drift 数据库 |

**建议：A。** 皮肤是文件（JSON + 图片），用文件系统最自然；`UserSettings` 只存一个 id 字符串，走你现有的 `settings_repository`。**不要把图片塞进数据库。**

---

### Q8 · 分发：本期做在线市场吗？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | 本期只做**本地导入**（文件选择器 + 文件夹/zip） |
| B | 顺带做市场（index.json 清单 + 下载） |

**建议：A。** 你已有 `file_picker` 和 `local_file_store`，本地导入几乎零成本。市场涉及托管、审核、版本管理，是独立项目，等有社区再说。但 **JSON 里预留 `srcUrl` 字段**（更新源），将来无痛接上。

---

### Q9 · 明暗模式与皮肤的关系？

`theme.json` 里有 `mode: light|dark|auto`。

| 选项 | 说明 |
|---|---|
| A | 皮肤自带 mode，用户不能覆盖 |
| **B（推荐）** | 皮肤声明默认 mode，用户可在设置里覆盖为 系统/亮/暗 |

**建议：B。** 三层优先级：**用户显式选择 > 皮肤的 `mode` > 系统**。一个暗色皮肤被用户在白天强制切亮色时，token 应做一次"智能反转"还是"原样使用"？建议 **原样使用并提示**（暗色皮肤强制亮色通常很丑，但用户的选择要尊重，且不该由我们替用户决定）。

---

### Q10 · 降级与容错策略

| 场景 | 建议行为 |
|---|---|
| theme.json 解析失败 | **回退内置 light**，设置页显示"该皮肤已损坏" |
| 缺少 token 字段 | **用内置默认值补齐**，不报错 |
| 背景图缺失 | 忽略背景图，其余照常 |
| 未知字段 | 忽略（不报错），仅 debug 日志 |
| 皮肤 id 冲突 | 内置皮肤优先，用户皮肤加后缀 |

**核心原则：皮肤永远不应该让 App 白屏。** 这条比"支持多少特性"重要得多。

## 二、我的整体建议（一句话版）

> **PR1 只做"Token 层 + 两个内置皮肤 + 接上 app.dart"，把 JSON 格式定死并写进 schema；
> 歌词窗口只派生 accent；用户旋钮做上；GUI 编辑器、SDUI、脚本层、市场全部后置。**

理由：你现在最大的不确定性不是"能做到多自由"，而是**"区域契约和 token 清单定得对不对"**。这个只有把 L1 跑起来、让官方皮肤真跑一遍才能验证。先把地基压实，上面的楼层才盖得稳。
